## How to work a story

1. Take the next story from `docs/crm/README.md` whose dependencies are all **done**. Do one story per session.
2. Read the story, then only the files under its **Read first**. Do not read the whole repository.
3. Implement it in small steps. After each step run `cargo check -p <crate>` and fix errors before going on.
4. Run every command in the story's **Verify** section and the gates below. All must pass.
5. Write `docs/crm/reports/<story-id>.md` from the template below.
6. Commit on `hermes/crm` with the message `feat(crm/<service>): <story-id> <title>` and stop. The supervisor reviews.

If you are stuck for more than three attempts on the same error, stop, write the report with **Status: blocked**, the
exact error and what you tried, and commit what compiles.

## How the code is shaped

- **Controllers** (`impl/src/controllers/<operationId>.rs`) are thin: first line `// BRRTRouter: user-owned`, build the
  context, check the role, call one service function, map the result. Return `HttpJson<serde_json::Value>` with
  `HttpJson::new(status, body)` so the same handler can return the success body or an `ErrorResponse`. The worked
  example is `microservices/crm/accounts/impl/src/controllers/list_accounts.rs` (with its `http_support.rs`,
  `auth.rs`, `database.rs`).
- **Services** (`impl/src/services/<area>.rs`) own the use case: one transaction, row-level security set by the
  context, audit and outbox rows in the same transaction.
- **Models** (`impl/src/models/<table>.rs`) are LifeModels exactly as the data-model YAML says.
- **Validators** (`impl/src/validators/<area>.rs`) hold rules the contract and database cannot express.
- **Money** is `rust_decimal::Decimal` inside, a decimal string on the wire. **Time** is `chrono::DateTime<Utc>`.
- **Ids** are UUID v7 generated by the service. **User ids** are Sesame `sub` strings.

## Never

- Never edit `gen/`, `openapi.yaml`, `asyncapi.yaml` or the data-model YAML. If one is wrong, report it.
- Never read or write another service's schema. Cross-service data comes through events or the other service's API.
- Never block a coroutine: BRRTRouter handlers run on `may` coroutines, so use the may-aware clients (Lifeguard,
  `may_minihttp`) and never `std::thread::sleep`, blocking DNS or a blocking HTTP client inside a handler.
- Never log personal data (emails, names, phone numbers, IPs) above debug.
- Never add a dependency that is not already in `microservices/Cargo.toml` `[workspace.dependencies]` without listing
  it in your report under **Needs approval**.
- Never commit secrets, tokens or real customer data. Seeds use `*.example` addresses.
- Never disable a test, a lint or a check to make it pass.
